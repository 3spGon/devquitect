# Devquitect Skill Development System concept

Status: Approved
Last updated: 2026-08-30

## Confirmed

- The repository contains three related Codex skills: software definition, approved plan execution, and targeted refactoring.
- The current repository has no repository-owned static validator, behavioral evaluation suite, CI workflow, plugin manifest, or reproducible release pipeline.
- The user wants good engineering practices for creating and evolving skills and agrees that controlled use of the skill under development is desirable.
- Human interaction design is not applicable: the proposed product is repository tooling, commands, reports, and release artifacts rather than a graphical interface.

## Assumptions

- The three skills should be developed independently but distributed together as a plugin named `devquitect`.
- The first release of the development system should favor portable, dependency-light local execution over provider-specific automation.
- Existing skill behavior is preserved unless a separate, explicitly reviewed behavioral change declares otherwise.

## Open decisions

No product decision blocks Gate 1. Tooling language, case serialization, CI provider, runner integration, and exact plugin metadata belong to technical design after approval.

## Problem

The skills encode consequential workflow, authorization, and persistence behavior, but changes are currently reviewed as Markdown alone. A syntactically valid edit can silently change implicit activation, permit an unauthorized mutation, break recovery, or make two skills overlap without any repository-owned mechanism detecting the regression.

## Desired outcome

A maintainer or contributor can modify or add a skill and use one documented local quality workflow to validate structure, exercise behavior in isolated environments, compare intended changes with a stable baseline, produce reviewable evidence, and build a reproducible plugin artifact from the verified commit.

## Actors

- **Maintainer** — defines skill behavior, owns compatibility decisions, and promotes verified releases.
- **Contributor** — proposes changes using repository-owned conventions and validation.
- **Reviewer** — evaluates the declared behavioral delta and its evidence.
- **Quality runner** — executes deterministic checks and isolated behavioral scenarios.
- **Codex runtime** — discovers and executes the packaged skills.
- **End user** — installs the plugin and invokes the skills explicitly or implicitly.

## System boundary

The proposed development system owns:

- authoring conventions and contributor guidance;
- structural and metadata validation;
- isolated fixtures and behavioral scenarios;
- deterministic assertions and independent semantic evaluation;
- stable-versus-candidate comparison;
- evidence and provenance reporting;
- plugin packaging, version checks, and release eligibility.

It does not own:

- public marketplace publication;
- application implementation generated by the skills;
- MCP servers, connectors, or external service integrations;
- deployment or mutation of external systems;
- exact textual equivalence of model responses;
- exhaustive testing of every model and reasoning configuration.

## Core workflow

1. A contributor starts from a named stable source version and declares the intended behavioral delta.
2. The contributor changes a candidate copy that is isolated from the active stable author version.
3. A single local quality entry point performs structural validation and applicable behavioral checks.
4. Behavioral cases execute in fresh workspaces and conversations, capturing observable actions and results.
5. The same representative cases can compare stable N with candidate N+1.
6. Deterministic invariants, independent semantic grading, and review establish whether the candidate is eligible for promotion.
7. Packaging uses the exact verified source revision and produces a reproducible `devquitect` plugin artifact.
8. A promoted N+1 may subsequently help define N+2.

## Controlled self-hosting rule

The project may use a stable Devquitect skill to help define its successor. The candidate cannot be its own sole authorizing authority, grader, or release decision-maker. Stable and candidate sources must remain isolated throughout an evaluation, and every report must identify both versions.

If the stable version cannot safely produce its successor, a documented manual or external skill-authoring recovery path is allowed, but the candidate remains subject to all independent validation and approval requirements.

## First-release scope

- Contributor-facing documentation and definition of done.
- Deterministic validation of skill structure, metadata, references, and packaging inputs.
- Isolated behavioral coverage for critical routing, read-only, authorization, persistence, and cross-skill boundaries.
- Immutable stable and candidate version selection with provenance in reports.
- Reproducible plugin packaging from verified source.
- Local release eligibility checks that can later be integrated with a CI provider.

## Non-goals

- Rewriting the three skills as part of the infrastructure change.
- Automatically approving Gate 1, Gate 2, releases, or behavioral expectation changes.
- Publishing the plugin publicly.
- Building a hosted evaluation service.
- Optimizing token cost before representative quality baselines exist.
